# 简历构建系统（一版一数据；模板一版一份，D 是例外）

数据 → 模板 → HTML + A4 PDF。四个版本**各有各的数据文件**，不共享任何字段；
模板通常一版一份，**只有 D 与 C 共用**（理由见下）。产物提交进仓库
（A/B/C 的 HTML 由站点发布，D 不上线；PDF 供从仓库直接下载）。

```
CV/
├── personal-photo.jpg          # 唯一照片资产（内联 base64 进产物，不属于「事实」，故不进数据文件）
├── RESUME_CONTENT.md           # docx 底稿存档，不参与构建
└── build/
    ├── build.py                # 构建：data/<版本>.yaml -> HTML 到 static/cv/、PDF 到 output/pdf/
    ├── validate.py             # 校验：各份数据承载的事实是否一致、页面上有没漏渲染
    ├── data/                   # ★ 要改内容就改这里
    │   ├── A-general.yaml      # 通用版
    │   ├── B-institute.yaml    # 研究院版
    │   ├── C-talent.yaml       # 人才计划版
    │   └── D-huawei.yaml       # 华为专供版（2026-10-08 新建，C 的派生版）
    ├── templates/              # 只管排版，不含任何内容
    │   ├── style-A-sidebar.html.j2        # 深蓝侧栏 + 白色正文（真双栏，含照片）
    │   ├── style-B-minimal.html.j2        # 极简单栏学术风（LaTeX 感，打印最佳，3 页，含照片+页脚页码）
    │   └── style-C-tech-timeline.html.j2  # 科技风·时间轴（hero + 时间轴，含照片；2026-09-30 起无渐变）
    │                                      # ↑ D 也用它——「一版一模板」的唯一例外
    └── output/
        ├── pdf/resume-{A-general,B-institute,C-talent,D-huawei}.pdf  # A 4 页、B/C/D 各 3 页（A4）
        └── html/resume-D-huawei.html      # ★ D 不上线，HTML 落在这里（其余三份见 static/cv/）

static/cv/                        # ★ A/B/C 的 HTML 产物在这里，**不在** build/output/ 下
    ├── resume-A-general.html
    ├── resume-B-institute.html
    └── resume-C-talent.html
```

> **为什么 HTML 产物不在 `build/output/` 里**（2026-10-03 搬迁）：主页头部要链接这三份简历，
> 而 Hugo 只发布 `static/` 下的东西。放进 `static/cv/` 后由 Hugo 原样复制到 `/cv/`，
> 线上可直接打开（`https://zeng-yirong.github.io/cv/resume-A-general.html`），
> 而且**没有第二份会漂移的副本**。PDF 不在站点上发布，仍留在 `build/output/pdf/`。
>
> **例外是 D**（2026-10-08）：本人选的是「只出文件，不上线」，所以它的 HTML 与 PDF 都出到
> `build/output/` 下、**不写进 `static/cv/`**，主页头部那行链接也不加它。开关是 `build.py` 的
> `VARIANTS["D"]["publish"]`（删掉那一行就改出到 `static/cv/`）。
> ⚠️ 不上线**不等于**秘密：仓库是公开的，`build/output/` 下的产物照样随 push 进 GitHub。
> 要连仓库都不进，得把这两个文件写进 `.gitignore`——那是另一种选择，当前没做。
>
> ⚠️ 这带来一条**静默失败**路径：`static/cv/` 里是提交进仓库的产物，而 CI 只跑
> `hugo --minify`、不跑 `build.py`。改了 `data/` 却忘了重跑并提交，线上就是旧简历，
> **Hugo 不会报任何错**。唯一防线是 `python validate.py --check-html`。

## 版本 ↔ 数据 ↔ 模板 ↔ 产物

| 版本 | 用途 | 数据文件 | 模板 | 产物 |
| --- | --- | --- | --- | --- |
| **A** | 通用版 | `data/A-general.yaml` | `style-A-sidebar.html.j2` | `resume-A-general.*` |
| **B** | 研究院版 | `data/B-institute.yaml` | `style-B-minimal.html.j2` | `resume-B-institute.*` |
| **C** | 人才计划版 | `data/C-talent.yaml` | `style-C-tech-timeline.html.j2` | `resume-C-talent.*` |
| **D** | 华为专供版 | `data/D-huawei.yaml` | 同上（与 C 共用） | `resume-D-huawei.*` |

一句话规则：`data/<名字>.yaml` → `resume-<名字>.*`（A/B/C 的 HTML 去 `static/cv/`，
D 的不上线、留 `output/html/`；PDF 一律留 `output/pdf/`）。
看到数据文件名就知道产物名，不用记第二个映射表。

## 日常用法

```bash
cd CV/build
python build.py                # 四份全出（HTML + PDF）
python build.py --style C      # 只出人才计划版（字母 = 数据与模板名）
python build.py --style D      # 只出华为专供版
python build.py --no-pdf       # 只出 HTML，秒级预览

python validate.py             # 各份数据事实一致？
python validate.py --check-html  # 再加：渲染结果没漏事实（需先 build）
```

> Windows 上请用 `python`（`python3` 会落到应用商店占位程序）。
> 本机用 miniconda 的 Python 3.13；依赖：`pip install pyyaml jinja2 playwright pypdf`
> 加 `python -m playwright install chromium`。

## 改内容的正确姿势

**同一批事实写了四遍**——这是「一版一数据结构」的代价，必须正视
（D 是 C 的派生版，跟着 C 一起改最省事：改完比对一下是不是只差那三处）：

1. 改任一份，就四份都改（论文、荣誉、经历、数字，四份里都有）。
2. 改完跑 `python build.py`，再跑 `python validate.py --check-html`。
3. 校验器不关心各份的 schema（那正是它们该不同的地方），只看：
   - **A↔B 的事实集合是否逐字相同**（自动收集每份 YAML 里所有字符串标量，
     按数据自己的分隔符 `· ： ； 、 ｜` 切碎后比较——允许重组，不允许丢失）。
     对 C 与 D 只报告差异、不判失败——各版服务不同场合，措辞允许各写各的；
     C/D 的事实覆盖另由下面的地标清单保证。**但「有差异」本身是信号**：
     2026-09-28 那天 C 被单独重写过、A/B 没跟上，校验器如实报出 66 项差异。
     同日 A/B 已按 C 同步完毕，现在三份的事实集合是一致的，
     再冒出差异多半就是「改了 C 忘了改 A/B」——先去同步，别往 `ONLY_IN` 里加。
     D 与 C 之间**已知且有意**的差异是 8 项（两段华为版简介的碎片 + 实习时间「至今」），
     项数变了才说明有人动过。
   - 一份**地标清单**（15 篇论文标题、6 项荣誉、9 条实习条目、关键数字…）
     是否各份都在——防的是「几份一起删掉」这种集合比较查不出的情况，也是 C 版事实不丢的主要保障。
     一条地标可以写成元组，允许各版用词不同（如 `("2 万条", "2+ 万条")`，C 就写成了后者）。
   - `--check-html`：数据里写了的，页面上是否都看得见（唯一能抓「模板漏渲染」的检查）。
4. 校验器报的差异**不要直接加进豁免清单**（`ONLY_IN` / `UNRENDERED`），先确认它是不是漏改。
   这两份清单里每条都写了理由；`UNRENDERED` 还会反向校验「豁免是否已失效」。

## 2026-09-28：A/B 的内容已按 C 同步（记住这条，否则会再漂一次）

（不抽共享内容层、不动 `build.py` 的架构）。所以这是一次**手工同步**，
不是一道以后自动成立的约束：

> **以后只改 C，A/B 就会再次漂移。** 改完 C 记得跑 `python validate.py --check-html`，
> 它会指名道姓地告诉你 A/B 少/多了哪一条——照着同步三份，别只改一份。

  头衔与身份是**两件事**：职位写「AI算法工程师」，身份「研究型实习生」放在正文里用
  「**作为**研究型实习生，负责…」连接——不要并排成两个身份（本人 2026-09-28 定）。

## 2026-09-29：B 压到 3 页（技能转注释 + 荣誉/项目并排）

本人要求：B 的技能段不显示、荣誉奖项与项目经历并排，把 PDF 从 4 页压到 3 页。做法三条：

1. **技能段转注释**（与 C 那条数字横条同一套办法）：`data/B-institute.yaml` 的 `sections` 里
   那条 skills 加了 `comment_only: true`，模板走注释分支——标记逐字写进一段 HTML 注释，
   页面上看不到、`grep` 得到。要恢复就删掉这个开关（`validate.py` 的 `UNRENDERED["B"]` 里
   同步列了技能里独有的字符串，删开关后那几条会报「豁免已失效」，照提示删掉即可）。
2. **荣誉奖项 + 项目经历并排**：写法和 C 一样，**机制是现成的、没新加**——
   `sections` 里写 `{pair: [左, 右], ratio: [a, b]}`（或两元素列表）就是一行两栏，
   `build.py` 的 `check()` 本来就认这种写法（此前只有 C 用）。B 的模板这一版才支持：
   段落渲染搬进了 `{% macro section(sec) %}`，循环按「单栏 / pair / 数组」分派。
   `ratio: [1.2, 0.8]` 是配出来的：奖项那栏条目多、是高的那栏，给它宽一点，
   原本折行的「中国科协青培…」那条收成一行，栏高从 261px 降到 241px。
3. **竖向间距收紧**（光并排还不够）：`section` 下边距 22→17px、`.entry` 12→9px、
   `h2` 下边距 12→10px、页眉与概要的下边距 24→20px、打印时 `.sheet` 上下内边距 44→36px。

**这类改动必须量着做，不能估。** 页数不是「内容总高 ÷ 页高」——不可分割的整块（并排行、
论文卡、段落标题）放不下就整块挪到下一页，白留一截页尾。这次正是如此：并排行高 241px
＋22px 外边距，而第 3 页只剩 239px，差 44px 就整块被挤到第 4 页；上面那 5 处收紧一共省下
约 66px，它才落回第 3 页。量的办法（临时脚本，用完即删）：

- Chromium 的打印布局是**连续排版**，所以取每个块的 `offsetTop` 就能预测断点：实测每页装得下
  **1070.2px** 文档流（A4 + `scale=0.95` + `@page{margin:14mm 0}`），页窗即 `[0,C)`、`[C,2C)`…；
  某块要落在第 3 页，需 `block_top + block_h + .sheet 下内边距 ≤ 3C`——**下内边距也算进流里**
  （漏算就低估 36~44px，恰好是这次差的那一点点）。量时 viewport 宽度必须是 A4 的 **794px**，
  用别的宽度量出来的高度不作数（第一次用 900px，白算一轮）。
- 最后仍以真 PDF 为准：见下面「本机调试小工具」。

**余量很薄，改完 B 必须复核页数**：并排行距 3 页上限只剩约 27px（一行半字），
任何「让正文变高」的改动（加文字、松间距、换字体）都可能把它顶回 4 页。
反过来 B 的末页还有约 130pt 空白，真要腾地方，可以从上面那 5 处间距里再抠。
（2026-10-08 更新：实习两条要点改长后这个上限已被吃到只剩 7px，见下面那节。）

**同一天页眉外链改成「图标 + 标签」后，那行不再折行**（原来明文 URL 会折到第二行），
页眉矮了一行：第 1 页页尾余量 54.2pt → 70.6pt，第 2/3 页与总页数一个没变。
**别把这一点余量当成新的余量**——它不足以把下一页的首块拉上来，所以只是第 1 页白得多一点，
并排行那约 27px 的上限没变（3 页结论也不受影响）。再改页眉（加外链、换行、加徽章）
要先按下面的办法量一遍，别直接假设「页眉的余量能兜住」。

**顺手记一个 Jinja 坑**：认「数组」时**不能**用 `row is sequence`——Jinja 的 `sequence`
测试只要求「有 `len`、能下标」，`dict` 也满足，于是单栏的 `{key: …}` 会被当成并排数组、
报 `has no element 0`。C 的循环里把 `is mapping` 写在前面、数组只作 `else`，就是这个原因
（B 这份照抄它的顺序，别再「顺手改成 sequence 更直观」）。

## 2026-10-08：实习两条要点改长 → B 的页底内边距 36→20px

本人重写了 C 版实习「Agentic RL 算法研发」组的两条要点（分隔符从 `,`/`；` 改成 `;`，
昇腾那条换成了「…发表首篇面向通用领域基于 GRPO 进行 Agentic Tool Use 训练的论文
【**Tool Zero, EMNLP 2025**; iTool, EMNLP 2025】」），按规矩同步进了 A/B 三份数据。
A 不变（仍 4 页）、C 不变（仍 3 页），**只有 B 掉到 4 页**：第 3 页原本装到 739pt，
改后只到 572pt，末页的并排行（荣誉奖项｜项目经历）整块被挪走。总流高只多了约 **20px**
——就是那条要点多折的一行。

**改法**：打印时 `.sheet` 的下内边距 `36px → 20px`。实测这是唯一的绑定项
（同一个 HTML 只改这一个值连续试）：36px → 4 页、**27px → 3 页、28px → 4 页**
——**边界就在 27/28 之间，当前的 20px 只剩 7px 余量**（不到一行字）。
选它而不是那 5 处竖向间距，是因为**这个下边距只落在文档流的最末尾**（末页最后一行之下），
压它不移动任何正文；那 5 处是配平过的，动哪一处都要重算一遍。
改完实测：3 页，末页末行 753pt（旧基线 739pt，多的 14pt 就是那条要点），
**离页脚（固定画在 y≈819pt）还有 65pt**。

> ⚠️ **更正一条旧说法**：「下内边距是末页内容与页脚条之间的余量」——**不是它保护的**。
> 页脚固定画在 y≈819pt，而内容盒由 `@page` 的 14mm 封在 803.3pt，两者差 16pt，
> 与 `.sheet` 的内边距无关。下边距唯一的作用是**总流高**，也就是只影响页数。

> ⚠️ **量尺常数已过期**：README 里「每页装得下 1070.2px 文档流」是 2026-09-30 量的，
> 之后 2026-10-04 页首内边距 36→10px，标尺跟着变了。这次实测的等价边界是
> 「块底 + `.sheet` 下内边距」≈ **3130–3138px 落在第 3 页容量内**（794px viewport 同一套量法）。
> 再量分页时别直接套 1070.2——**用「改一个值、渲染一次、数页数」的翻页法**，
> 一次 2 秒，比推公式可靠。

## 2026-09-30：B 的观感统一（计数上色、标签成规则、页脚页码）

本人看过三页成品后挑了七处，都是「信息层级」问题而不是好不好看。逐条记下改法与坑：

1. **「一作/共一 9 篇」原来被当成英文**：它跟在 `.en` 里，于是 10px 淡灰 + 字距 1px，
   全份最能打的数字反而最淡。现在拆成 `.cnt`（无衬线、强调色、字距 0）跟在标题后，
   英文槽只留纯英文。**h2 是 flex + space-between**：要「标题 + 计数」作为一组靠左，
   得把两者一起包进一个 `<span>`，直接塞第三个子元素会被摊到中间去。
2. **「在投」标签的棕色是全份唯一的例**：`#8a5a3b` 这个棕不在「绿 + 中性灰」里。
   顺手把标签风格定成规则，写进 CSS 与本节：**描边 = 身份/状态；填充 = 成就/计数**。
   按此，页眉的 `.hb`（身份）与 `.tag.P`（状态）描边，`.badge`、`.tag.A`/`.tag.B`（成就）填充。
   **加新标签前先读这条**：加 1px 边框的同时把 padding 从 6px 收到 5px，否则会比别的标签宽。
3. **页眉照片改成对整块居中**（`align-items:flex-start` → `center`）：文字块有 5 行约 186px、
   照片只有 104px，顶对齐会让照片「挂」在右上角。照片比文字块矮，所以行高仍由文字块决定

## 页脚页码（`page_numbers`，B/C 开，A 没开）

数据的顶层加一行 `page_numbers: true` 就有页码，删掉就没有——**是显示开关，不是内容**。
渲染出的字是「第 x 页 / 共 y 页」（`build.py` 的 `PAGE_FOOTER`），居中、8pt、`--muted` 同色。

**为什么必须用 Chromium 的 footer、不能靠 CSS**：Chromium 至今不支持 `@page` 的页边内容
（`@bottom-center` 那一套），HTML 里也没有 page 计数器——CSS 方案在这条链路上做不到。

**关键：页脚落在正文够不着的地方，所以不吃正文高度。** B 的 `@page{margin:14mm 0}` 本来就在
页底留了 14mm 空白（正文最多写到 803pt、页高 843pt），页脚落进去（实测 y≈819pt），
所以**页数与正文位置都不动**——这也是这条能安全加上去的原因。两个坑都踩过：

- **`display_header_footer=True` 会把页眉一起打开**：不给 `header_template` 的话 Chromium
  会画它自带的默认页眉（日期 + 网页标题 + 网址），每页顶上一行
  「2026/9/30 00:16 曾屹荣 · 简历 — 样式B：…」。所以必须显式传一个「有内容但看不见」的
  div（`PAGE_HEADER`）——传空串会被当成没给、又退回默认页眉。
- **别顺手去传 margin**：留白由模板 CSS 的 `@page` 控制，CDP 传了边距会把 CSS 的值覆盖掉，
  正文区跟着变、分页全乱。代码里保持 `margin` 全 0 就是这个原因。

**`@page` 下边距的真正作用（2026-09-30 给 C 加页码时才量清楚）**：**页脚的位置不随它变**——
Chromium 把页脚画在固定的 y≈819pt，B 的 14mm 与 C 试过的 7mm/10mm 都落在同一个 y。
这个 margin 唯一的作用是**压低内容盒的底**，让正文够不着页脚。所以它不能小气：
C 试 7mm 时内容盒底是 824pt，已经低于页脚的 819pt，正文一写满就压在页码上；
**10mm（内容盒底 805pt、离页脚 14pt）是实测能用的最小值**。

`build.py` 的 `FOOTER_BAND` 登记了每版的 `@page` 原文，`check()` 会去模板里逐字比对——
把 `@page` 改回 `margin:0`、或改了模板忘了改登记，都会当场报错，
而不是等印出来才发现页码叠在字上。没登记的版式开 `page_numbers` 会被直接挡掉（A 就是）。

**A 现在开不了**：它的 `@page{margin:0}`（留白靠元素自身 padding），底部没有那条带子，
页脚会被画到正文上。要给它加页码，得先让出底部留白（A 每页余量只有 50pt 上下，
让出 10mm 就等于每页少 3 行），再按上面的办法重新量分页。

**还有一处只做了一半**：页码在 PDF 里，**HTML 产物里没有**（它是 Chromium 打印期画的）。
所以拿 HTML 在浏览器里直接打印，不会带页码。

### 2026-09-30：C 加页码 + C 的核心顺序改成与 B 一致

## 本机调试小工具（分页与版式核对）

按顺序做这三件事，能抓出所有的分页缺陷（第 1→2 页那种「最后一条要点被甩到下一页顶端」
和「在投论文小标题孤零零留在页尾」就是这么抓出来的）：

# 2) 每页首尾文字的真实位置（pymupdf 的 y 是从上往下，单位 pt，A4 页高 843）
python -c "
import pymupdf; d = pymupdf.open('output/pdf/resume-C-talent.pdf'); H = d[0].rect.height
for i, pg in enumerate(d, 1):
    ws = sorted(pg.get_text('words'), key=lambda w: w[1])

    print(f'第{i}页 顶 {line(ws[0][1])} ｜ 底 {line(ws[-1][1])} ｜ 底部余量 {H-ws[-1][1]:.0f}pt')"

看**每页首行是不是一个完整的开头**（段落标题 / 条目开头 / 一句完整的话）、
**末行是不是一个完整的结尾**。若首页行是一句话的续行、或末行是 `•` 这种孤零零的项目符号，就是被劈开了。
第 3 步：把页缝渲染成图目视（红线 = 页缝），截完用 Read 看图——

```python
import pymupdf, os
from PIL import Image
d = pymupdf.open(r"...\output\pdf\resume-C-talent.pdf")
Z, H, W = 1.9, d[0].rect.height, d[0].rect.width

def shot(page, top, height):          # 裁 page 页上从 top 开始、高 height 的一条
    pix = d[page].get_pixmap(matrix=pymupdf.Matrix(Z, Z), clip=pymupdf.Rect(0, top, W, top + height))
    return Image.frombytes("RGB", (pix.width, pix.height), pix.samples)

for i in range(d.page_count - 1):     # 上页底 150pt + 红缝 + 下页顶 150pt
    a, b = shot(i, H - 150, 150), shot(i + 1, 0, 150)
    img = Image.new("RGB", (a.width, a.height + 14 + b.height))
    img.paste(a, (0, 0))
    img.paste(Image.new("RGB", (a.width, 14), (220, 38, 38)), (0, a.height))
    img.paste(b, (0, a.height + 14))
    img.save(os.path.expandvars("%TEMP%") + f"/seam{i+1}{i+2}.png")
```

## 不要做的事

- **不要直接编辑产物**（`static/cv/*.html` 与 `output/pdf/*.pdf`）：它们是产物，
  `python build.py` 一跑就覆盖。改文字要改 `data/*.yaml`（改版式才动 `templates/*.j2`）。
  2026-09-28 就发生过一次：在产物 HTML 里改了 60 多处文字，重建后全部丢失，只能再逐条搬回数据文件。
  2026-09-29 又一次（小的）：产物里多了「主流」两个字，重建就没了，见上面那节。
  所以**重建前先备份产物**，重建后核对产物与数据——`validate.py --check-html` 报出
  「数据里有、页面上看不到」的条目，多半就是产物里那处手改被覆盖了（反过来，产物比数据多出的
  字它查不到，所以文字层面的核对还得把备份与产物对一遍）。
- 不要把 HTML 产物挪回 `build/output/`：它们必须在 `static/cv/` 下才会被 Hugo 发布到站点上
  （见开头那节）。挪回去线上链接就 404。
- 不要把 `output/` 或 `static/cv/` 加回 `.gitignore`：产物是刻意提交的，忽略它会让新产物在
  `git add .` 时被静默漏掉。
- 不要给 `data/` 再引入一份「共享基础数据 + 各版覆盖」的文件：那正是这次重构去掉的东西
  （需要溯源看 `git show fadb334:CV/build/resume.yaml`）。
